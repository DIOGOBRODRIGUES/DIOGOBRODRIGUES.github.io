Histórico

Banco de dados relacional

Modelo consolidado com forte organização em tabelas, linhas, colunas, chaves e integridade.

Termo NoSQL

O termo passa a aparecer para indicar soluções não relacionais e propostas alternativas.

Fortalecimento do NoSQL

Com Big Data e aplicações web massivas, a adoção cresce em cenários distribuídos.

Por que o NoSQL ganhou força?

  • A cada ano, a quantidade de dados cresce em ritmo acelerado.
  • Muitos sistemas passaram a lidar com alto volume, variedade e velocidade de dados.
  • Em vários cenários, o modelo relacional tradicional não era a solução mais adequada em custo e escala.
Ambientes distribuídos e cargas crescentes foram o cenário que impulsionou o NoSQL.

NoSQL substitui SQL?

SQL

Continua essencial em sistemas com forte consistência, transações complexas, relatórios estruturados e regras rígidas de integridade.

NoSQL

É indicado quando há grande escala, dados semiestruturados, distribuição e necessidade de flexibilidade de schema.

Ideia central: na prática, não é uma substituição total; muitas arquiteturas usam as duas tecnologias simultaneamente.

Uso simultâneo de SQL e NoSQL

  • SQL: cadastro de usuários, pagamentos, pedidos, notas fiscais, controle acadêmico.
  • NoSQL: logs, sessões, cache, recomendação, dados de sensores, catálogos flexíveis.
  • Essa abordagem é comum em arquiteturas modernas e é chamada de persistência poliglota.
Uma aplicação real costuma combinar modelos para atender partes diferentes do negócio.

Cadastro de Itens

Catálogos flexíveis

No e-commerce e em marketplaces, itens de categorias diferentes pedem estruturas diferentes.

  • SQL tende a gerar muitas colunas vazias ou tabelas extras.
  • NoSQL guarda cada produto como um documento com os campos que ele realmente precisa.
  • Isso acelera a leitura pelo front-end e simplifica a evolução do catálogo.
Produtos com atributos diferentes encaixam melhor em documentos flexíveis do que em esquemas rígidos.

Cadastro de Usuários

Perfil de usuário

Na web moderna, perfis mudam com frequência e normalmente precisam de leitura rápida.

  • Nome, foto, preferências e tema claro/escuro combinam bem com NoSQL.
  • O schema flexível acompanha a evolução do aplicativo sem grandes migrações.
  • O perfil pode ficar no NoSQL enquanto ações financeiras continuam no SQL.
Perfis de usuário favorecem leitura rápida e mudanças frequentes na estrutura dos dados.

A Regra de Ouro

Use NoSQL quando...
  • você precisa de flexibilidade de schema;
  • há grande volume com leitura em massa;
  • o sistema exige escala rápida e dados que mudam muito.
Use SQL quando...
  • a integridade dos dados é inegociável;
  • há relacionamento forte entre entidades;
  • o processo envolve transações complexas e ACID.
A decisão não depende de ser “usuário” ou “item”, mas do que acontece com esses dados: catálogo, navegação e perfil pedem agilidade; cartão, pedido e nota fiscal pedem segurança.

Escalabilidade

Relacional = vertical

  • Aumento de CPU, memória e disco do mesmo servidor.
  • Mais simples no início.
  • Pode se tornar caro e limitado.

NoSQL = horizontal

  • Distribuição em vários nós.
  • Uso de particionamento e sharding.
  • Escala melhor para grandes volumes e alta concorrência.

Vantagens da escalabilidade horizontal

  • Permite crescer adicionando novos servidores ao cluster.
  • Reduz gargalos concentrados em uma única máquina.
  • Favorece alta disponibilidade e tolerância a falhas.
  • Pode oferecer melhor relação custo-benefício em ambientes de grande escala.

Estruturas de dados

Banco relacional

  • Modelagem de dados prévia.
  • Tabelas, colunas, tipos, relacionamentos e chaves primárias/estrangeiras.
  • Maior padronização e consistência estrutural.

Banco não relacional

  • Schema-free ou schemaless.
  • Mais flexibilidade para documentos, chave-valor, grafos e colunas.
  • Adaptação mais rápida a mudanças nos dados.

Quando usar cada abordagem?

Prefira SQL quando...

  • houver integridade rigorosa;
  • existirem transações críticas;
  • o modelo de dados for estável e altamente relacional.

Prefira NoSQL quando...

  • o volume crescer muito;
  • os dados variarem com frequência;
  • a aplicação exigir distribuição e elasticidade.

Exemplo prático de arquitetura híbrida

  • Universidade: matrículas, notas e financeiro em SQL.
  • Ambiente virtual: logs de acesso, trilhas de navegação e recomendações em NoSQL.
  • Resultado: cada tecnologia é usada no cenário em que entrega mais valor.
Arquiteturas híbridas permitem responder melhor a diferentes tipos de demanda.

NoSQL por modelo de uso

Documento

Ideal quando cada registro pode ter estrutura diferente, como produtos, perfis e catálogos flexíveis.

Chave-valor

Excelente para cache, sessão de usuário, tokens e dados com leitura extremamente rápida.

Coluna

Bom para grandes volumes distribuídos, escrita intensa e escalabilidade horizontal.

Grafo

Indicado quando entender relações é tão importante quanto armazenar os dados em si.

Banco de dados NoSQL em grafos

Conceitos centrais

  • Nós: representam entidades, como Cliente, Produto, Filme ou Professor.
  • Vértices / relacionamentos: representam conexões entre os nós.
  • No modelo de grafos, o relacionamento deixa de ser detalhe e vira parte central da consulta.
Em bancos de grafos, entidades e conexões são consultadas como parte do mesmo modelo.

Aplicações de bancos em grafos

Redes sociais

Amizades, seguidores, bloqueios, recomendações e comunidades.

Detecção de fraude

Descoberta de conexões suspeitas entre contas, cartões, IPs e dispositivos.

Recomendação

Produtos, filmes, músicas e perfis semelhantes a partir de relações.

Na prática: Neo4j

Neo4j é um dos bancos de dados em grafos mais conhecidos e aparece no ranking DB-Engines como o principal destaque desse modelo [page:1].
  • Permite modelar entidades como nós e conexões como relacionamentos.
  • Usa a linguagem Cypher para criação e consulta de grafos.
  • Ambiente de testes: sandbox.neo4j.com.
Neo4j é bastante usado para explorar visualmente relações entre entidades e padrões de conexão.

Cypher: criando um nó

Exemplo


CREATE (:Cliente {
  name: "Diana",
  age: 18,
  hobbie: ["tocar teclado", "ver filmes"]
})
Aqui criamos um nó do tipo Cliente com propriedades como nome, idade e hobbies.

Cypher: consultando um nó

Consulta por padrão


MATCH (d:Cliente {name: "Diana"})
RETURN d

Observação importante

Em Cypher, normalmente declaramos uma variável para o nó, como d, e depois a retornamos na consulta.

Forma mais adequada do que escrever apenas MATCH(Diana) RETURN Diana [web:16].

Criando nós e relacionamentos

Exemplo com relacionamento


CREATE (:Cliente {name: "Bianca", age: 17, hobbie: ["Andar de bicicleta"]})
-[:BLOQUEOU]->
(:Cliente {name: "Tatiana", hobbie: ["tocar teclado"]})
Bianca nó de origem
BLOQUEOU relacionamento
Tatiana nó de destino

Leitura do relacionamento no grafo

  • Cada nó representa uma entidade do domínio.
  • Cada aresta mostra como uma entidade se conecta a outra.
  • Isso facilita perguntas como: “quem bloqueou quem?”, “quem conhece quem?” ou “quais perfis têm interesses em comum?”.
Em grafos, as consultas percorrem conexões, o que é muito útil em redes sociais, recomendação e análise de fraude.

Banco de dados baseados em colunas

Definição: bancos NoSQL baseados em colunas, também chamados de wide-column stores, organizam os dados em famílias de colunas e são muito usados em cenários distribuídos e escaláveis.
  • São indicados para grandes volumes de dados.
  • Funcionam bem em arquiteturas distribuídas.
  • Têm destaque em cenários com acesso massivo e alta escalabilidade.
Wide-column stores são usados quando a aplicação precisa crescer em volume, distribuição e disponibilidade.

Terminologia essencial

Keyspace

Equivale, didaticamente, ao “banco de dados” principal onde ficam as estruturas internas.

Column Family

Termo histórico do Cassandra para o agrupamento lógico de colunas; em CQL moderno, aproxima-se da ideia de tabela.

Row Key

Chave que identifica e ajuda a distribuir os dados; também associada ao conceito de partition key.

Mais termos importantes

Column

Representa o dado armazenado em uma determinada estrutura da linha, como um atributo ou célula.

Partition Key

Define como os dados serão distribuídos entre os nós do cluster, sendo central para escalabilidade horizontal.

Em Cassandra, modelar bem a chave de partição é uma decisão crítica, porque ela influencia diretamente distribuição, consulta e desempenho.

Exemplo de aplicação: registro de transações

  • Uma empresa pode registrar milhões de transações por dia.
  • Cada transação pode ser gravada com chave de partição baseada, por exemplo, no cliente ou na data.
  • O modelo favorece armazenamento distribuído e recuperação rápida por chave.
Registros massivos, históricos e distribuídos são cenários típicos para wide-column stores.

CQL: visão inicial

CQL significa Cassandra Query Language e foi criada para oferecer uma sintaxe familiar para quem já conhece SQL, mas adaptada ao funcionamento do Cassandra.
DDL Criação de keyspace e tabelas.
DML Inserção, atualização e leitura de dados .
Modelo Sintaxe parecida com SQL, mas com regras próprias de particionamento.

Comando básico: criação de keyspace

Exemplo em CQL


CREATE KEYSPACE loja
WITH replication = {
  'class': 'SimpleStrategy',
  'replication_factor': 1
};
Esse comando cria um keyspace, que funciona como o contêiner principal dos dados no Cassandra.

Comandos básicos em sequência


USE loja;

CREATE TABLE transacoes (
  id UUID PRIMARY KEY,
  cliente TEXT,
  valor DECIMAL,
  data_transacao DATE
);

Após criar o keyspace, usamos USE para selecioná-lo e depois criamos uma tabela com chave primária e colunas básicas em CQL.

Ideia final sobre bancos em colunas

Wide-column não é “SQL com outro nome”

Resumo: bancos baseados em colunas foram projetados para escala horizontal, distribuição e grande volume de dados, com destaque para Apache Cassandra no ranking atual.

A modelagem correta da chave e da forma de acesso é decisiva para obter desempenho e disponibilidade nesse tipo de banco.

Banco de dados chave-valor

Definição: bancos chave-valor armazenam os dados no formato chave → valor, priorizando acesso simples e rápido.
  • A chave identifica unicamente o registro.
  • O valor pode ser simples, como texto e número, ou mais complexo.
  • É muito usado em cache, sessão, preferências e configuração .
Bancos chave-valor priorizam acesso direto por chave e baixa latência .

Quando usar chave-valor?

Sessões Armazenamento rápido de login, token e estado do usuário [web:45].
Cache Reduz consultas repetidas e acelera respostas.
Configurações Preferências, parâmetros e valores simples por chave.
Tempo real Útil em cenários com leitura rápida e frequente .

Banco de dados baseado em documentos

Definição

Bancos orientados a documentos armazenam dados em estruturas semelhantes a JSON, com campos simples e aninhados .

Vantagem principal

Oferecem schema flexível, facilitando adaptação da base à evolução da aplicação .

Um banco de documentos pode representar pares chave-valor, mas vai além disso, pois permite documentos complexos, consultas ricas e índices avançados.

Introdução ao MongoDB

  • MongoDB é um banco de dados orientado a documentos.
  • Os dados são armazenados em documents e organizados em collections .
  • É muito usado em APIs, aplicações web, catálogos e perfis de usuário.
  • É uma das principais referências NoSQL da atualidade .
O MongoDB trabalha com coleções, documentos e recursos de escalabilidade .

Instalação

Modo local

O MongoDB Community Edition pode ser instalado localmente em Windows, macOS e Linux.

Ferramentas

Depois da instalação, o aluno pode usar o MongoDB Shell para testar comandos e operações básicas.

Em aulas práticas, a instalação local é útil para laboratório, enquanto a versão online simplifica o primeiro contato com a plataforma.

MongoDB online

MongoDB Atlas é o serviço online e gerenciado da plataforma, permitindo criar clusters na nuvem sem instalar manualmente o banco.
  • Permite criar cluster gratuito para estudo.
  • Permite gerenciar usuários, rede e conexão.
  • Pode ser acessado por drivers, shell e interface web
MongoDB Atlas facilita implantação, conexão e gerenciamento online .

Schema Design

O que é?

Schema design é o planejamento da estrutura de documentos, coleções e relacionamentos da aplicação.

Ideia central

No MongoDB, o schema deve ser pensado com base no modo como o sistema lê, grava e consulta os dados .

A modelagem em MongoDB costuma partir das consultas e do uso real da aplicação.

Boas práticas

Modelar pelas consultas

Estruture os documentos pensando nas consultas mais frequentes.

Usar embedding com critério

Dados pequenos e fortemente ligados podem ficar no mesmo documento.

Indexar com cuidado

Índices ajudam consultas, mas também geram custo de manutenção.

JSON vs BSON

JSON

  • Formato textual e legível.
  • Muito usado em APIs e aplicações web.

BSON

  • Formato binário usado pelo MongoDB para armazenar documentos.
  • Suporta tipos adicionais como Date, ObjectId e dados binários.
JSON é mais fácil de ler; BSON é o formato interno otimizado que o MongoDB utiliza.

Operação e manipulação de dados

Insert Inserção de documentos em coleções.
Find Consulta de documentos com filtros.
Update Alteração parcial ou total de documentos.
Delete Remoção de documentos da coleção.

Essas operações compõem o CRUD básico do MongoDB.

Exemplo básico de manipulação


db.clientes.insertOne({
  nome: "Ana",
  idade: 22,
  curso: "ADS"
})

db.clientes.find({ curso: "ADS" })

db.clientes.updateOne(
  { nome: "Ana" },
  { $set: { idade: 23 } }
)

db.clientes.deleteOne({ nome: "Ana" })

Performance e índices

  • Índices aceleram consultas recorrentes.
  • Sem índice, o banco pode precisar varrer muitos documentos.
  • Com índice, a busca fica mais eficiente.
  • Índices em excesso aumentam custo de armazenamento e escrita.

Exemplo


db.clientes.createIndex({ nome: 1 })

Esse índice favorece pesquisas pelo campo nome [web:56].

Agregação

Ideia central

A agregação processa múltiplos documentos e retorna resultados calculados, geralmente por meio de um pipeline.

Exemplos de uso

Filtrar, agrupar, ordenar, somar, contar e gerar relatórios analíticos sobre os dados.

Exemplo de agregação


db.vendas.aggregate([
  { $match: { status: "pago" } },
  { $group: { _id: "$curso", total: { $sum: "$valor" } } },
  { $sort: { total: -1 } }
])
Nesse pipeline, primeiro filtramos os documentos pagos, depois agrupamos por curso e por fim ordenamos do maior total para o menor [web:53][web:54].

Fechamento: MongoDB

Resumo: MongoDB combina flexibilidade de schema, documentos em BSON, índices e pipeline de agregação, sendo uma das principais tecnologias NoSQL atuais.

Boa modelagem, uso cuidadoso de índices e entendimento entre JSON e BSON são fundamentais para desempenho e organização.
