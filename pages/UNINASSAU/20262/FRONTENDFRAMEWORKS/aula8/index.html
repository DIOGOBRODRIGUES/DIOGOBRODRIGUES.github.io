DOIS PROBLEMAS DIFERENTES

Autenticação não é autorização

ID Autenticação

“Quem é você?”

login, credencial, sessão
✓ Autorização

“O que você pode fazer?”

papel, permissão, recurso

Um usuário autenticado pode acessar qualquer tela?

Tempo sugerido: 4 minutos. Fala sugerida: “Entrar no prédio não dá acesso automático a todas as salas.” Pergunta: um estudante logado deve poder excluir usuários? Resposta: só se tiver permissão. Para esta aula, implemente autenticação e uma autorização binária simples: há sessão ou não. Não aprofunde papéis. Erro frequente: chamar qualquer 403 de falha de login. Transição: acompanhe o percurso completo de uma tentativa de entrada.

Qual estado impede dois envios rápidos do mesmo formulário?

Tempo sugerido: 5 minutos. Resposta esperada: o estado de envio, usado para desabilitar o botão enquanto a Promise está pendente. Peça que a turma compare mensagem genérica de erro com “usuário ou senha inválidos”. Evite revelar se o usuário existe em um sistema real. Erro frequente: limpar o erro só depois de uma nova falha. Sugestão: setErro('') antes da requisição. Transição: isole a comunicação em um serviço.

SERVIÇO DE AUTENTICAÇÃO

A função devolve dados ou lança erro

export async function autenticar(username, password) {
  const response = await fetch('https://dummyjson.com/auth/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ username, password }),
  })

  const data = await response.json()
  if (!response.ok) throw new Error(data.message ?? 'Falha no login')

  return data
}

src/services/authService.js

Tempo sugerido: 7 minutos. Leia por blocos destacados. Pergunte se fetch rejeita automaticamente uma resposta HTTP de erro. Resposta: não necessariamente; por isso verificamos response.ok. Explique que response.json também é assíncrono. O serviço não conhece React, estado nem navegação. Erro frequente: retornar response em vez de data. Fonte: https://developer.mozilla.org/docs/Web/API/Fetch_API/Using_Fetch e https://dummyjson.com/docs/auth. Transição: a página coordena o serviço com os estados visuais.

COORDENAÇÃO NO COMPONENTE

O submit controla a experiência

async function handleSubmit(event) {
  event.preventDefault()
  setEnviando(true)
  setErro('')
  try {
    const data = await autenticar(username, password)
    onLogin(data)
    navigate('/painel', { replace: true })
  } catch (error) {
    setErro(error.message)
  } finally {
    setEnviando(false)
  }
}

A página pede autenticação. App mantém a sessão.

Tempo sugerido: 7 minutos. Pergunte o que aconteceria sem preventDefault. Resposta: o envio tradicional recarregaria o documento. Destaque a prop onLogin: LoginPage recebe a função, mas o estado de sessão ficará no ancestral que também monta as rotas. Explique replace: o botão voltar não deve levar novamente ao formulário após o login. Erros frequentes: esquecer await, navegar antes de onLogin, deixar o botão desabilitado após erro por ausência de finally. Transição: programaremos apenas o caminho mínimo antes de melhorar a experiência.

BLOCO 2

Permanecer

Representar e restaurar a sessão sem guardar a senha

Tempo sugerido: 1 minuto. Fala sugerida: “Entrar funciona. Agora pressione F5.” O desaparecimento da sessão cria a necessidade da persistência, que a turma já conhece com localStorage. Transição: escolha conscientemente o que salvar.

MINIMIZAÇÃO DE DADOS

Sessão não é cópia do formulário

Guardar neste exercício id e nome exibido username accessToken
Não guardar senha campos desnecessários segredos da aplicação

Para sistemas reais, o back-end pode preferir cookies seguros e inacessíveis ao JavaScript.

Tempo sugerido: 5 minutos. Fala sugerida: “Guardar menos reduz exposição e simplifica o estado.” Explique que localStorage é legível por JavaScript e, portanto, tokens ali podem ser afetados por XSS. Para o exercício com API pública, o armazenamento local permite praticar a sessão. Em produção, cookies HttpOnly, Secure e SameSite podem ser preferidos conforme a arquitetura. Pergunta: por que nunca guardar senha? Resposta: ela não é necessária depois do login e sua exposição teria impacto grave. Transição: inicialize o estado com o valor persistido.

ESTADO ↔ ARMAZENAMENTO

Ler uma vez. Gravar quando entrar.

AO CRIAR O ESTADO 
const [sessao, setSessao] = useState(() => {
  try {
    const salva = localStorage.getItem('sessao')
    return salva ? JSON.parse(salva) : null
  } catch {
    return null
  }
})
DEPOIS DO LOGIN 
function entrar(data) {
  const sessaoMinima = {
    id: data.id,
    nome: data.firstName,
    username: data.username,
    accessToken: data.accessToken,
  }
  setSessao(sessaoMinima)
  localStorage.setItem('sessao', JSON.stringify(sessaoMinima))
}
Tempo sugerido: 7 minutos. Leia o inicializador funcional: ele consulta o armazenamento apenas na criação inicial do estado. Pergunte por que existe try/catch. Resposta: o valor pode estar corrompido e JSON.parse pode lançar erro. Mostre que localStorage só armazena texto. Ordem de setSessao e setItem não é crítica aqui, mas os dois precisam usar o mesmo objeto mínimo. Erro frequente: localStorage.setItem('sessao', sessaoMinima), que salva “[object Object]”. Fonte: https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage. Transição: sair precisa desfazer os dois lados.

CICLO COMPLETO

Reload restaura. Logout remove.

Loginestado + localStorage
→
ReloadlocalStorage → estado
→
Logoutestado = null + removeItem
function sair() {
  setSessao(null)
  localStorage.removeItem('sessao')
}
Tempo sugerido: 5 minutos. Peça que a turma identifique qual teste pega uma implementação incompleta: login, reload e logout, nessa ordem. Se remover apenas o estado, o reload recupera a sessão antiga. Se remover apenas o localStorage, a tela atual ainda pode considerar o usuário logado. Após sair, navegue para /login ou deixe o guard fazer isso. Erro frequente: usar localStorage.clear(), que apaga dados não relacionados do aplicativo. Transição: conecte e teste ao vivo.

LIVE CODING

O teste é uma sequência de ações

Entrar→ Inspecionar→ Atualizar→ Sair→ Atualizar

Que resultado provaria que o logout ficou incompleto?

Tempo sugerido: 10 minutos. Demonstração: implemente o inicializador, entrar e sair. Abra DevTools > Application > Local Storage e mostre o objeto. Atualize a página após login e após logout. Resposta à pergunta: o usuário reaparecer depois do reload, ou a rota protegida continuar acessível. Provoque um JSON inválido manualmente para justificar o try/catch e depois remova-o. Não salve a senha nem o estado inteiro do formulário. Erros frequentes: chaves diferentes na leitura e escrita, JSON.parse aplicado duas vezes e setter dentro do inicializador. Transição: com uma sessão confiável, a rota pode tomar uma decisão.

BLOCO 3

Proteger

Decidir entre renderizar a página ou redirecionar

Tempo sugerido: 1 minuto. Fala sugerida: “A rota protegida é uma condição de renderização aplicada ao roteamento.” Esclareça que o exemplo usará children e Navigate, sem Outlet ou rotas aninhadas. Transição: leia o componente como uma pergunta booleana.

COMPONENTE DE GUARDA

Há sessão?

import { Navigate } from 'react-router-dom'

export function RotaProtegida({ sessao, children }) {
  if (!sessao) return <Navigate to="/login" replace />
  return children
}
sessão?
não/login
simchildren
Tempo sugerido: 7 minutos. Fala sugerida: “O componente não valida a senha. Ele lê o resultado atual: existe sessão?” Pergunte o que children representa. Resposta: o elemento envolvido pela rota protegida. Explique replace: evita que a entrada bloqueada permaneça como etapa útil no histórico. Erros frequentes: importar Navigate de pacote errado, escrever navigate em minúscula, devolver string '/login' e esquecer return. Fonte: https://reactrouter.com/api/components/Navigate. Transição: use o guard na configuração que a turma já conhece.

NA CONFIGURAÇÃO DE ROTAS

A proteção envolve apenas o que precisa

<Routes>
  <Route path="/" element={<HomePage />} />
  <Route path="/login" element={<LoginPage onLogin={entrar} />} />

  <Route
    path="/painel"
    element={
      <RotaProtegida sessao={sessao}>
        <PainelPage sessao={sessao} onLogout={sair} />
      </RotaProtegida>
    }
  />
</Routes>

Página pública continua pública. Página privada passa pelo guard.

Tempo sugerido: 7 minutos. Pergunte se /login deve ficar dentro da rota protegida. Resposta: não, senão o usuário sem sessão seria redirecionado para uma tela também bloqueada. Demonstre digitando /painel em uma aba anônima. Depois faça login e repita. Erros frequentes: proteger a própria rota de login, manter sessao em LoginPage e não em App, e esquecer BrowserRouter no ponto de entrada. Transição: estabeleça o limite de segurança dessa técnica.

LIMITE DA PROTEÇÃO

O guard protege a experiência, não a API

1 Front-end

oculta ou redireciona a interface

2 Back-end

valida token e permissão em cada endpoint

Código enviado ao navegador pode ser inspecionado. Dados sensíveis só saem do servidor após validação.

Tempo sugerido: 5 minutos. Fala sugerida: “Rota protegida no React melhora o fluxo, mas não transforma o navegador em cofre.” Pergunte como alguém poderia chamar a API sem usar a tela. Respostas: DevTools, Postman, outro script ou cliente. Portanto, o servidor deve recusar requisições sem credencial válida. Erro frequente: carregar dados privados e apenas esconder com CSS. Transição: o servidor comunica a causa com códigos HTTP.

Tempo sugerido: 5 minutos. Pergunte: “Usuário logado tenta uma ação exclusiva de administrador. Qual código faz sentido?” Resposta: 403. “Token expirou?” Resposta: 401. Esclareça que o endpoint didático de login pode usar outro status para credenciais inválidas; a tabela descreve a semântica dos recursos protegidos. Fontes: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/401 e https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/403. Transição: conecte essas respostas ao estado da sessão.
